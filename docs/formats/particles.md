# Дым из-под колёс (частицы гонки)

Статус 2026-09-19. Выведено из нашего дизассемблирования (objdump) и псевдо-C Ghidra дампов `work/re/race_demo`,
`work/re/race_load` (US Simulation v1.2, SCUS_944.88, EXE SHA-1 3030aa271c0a4022fc69ce09d76a6bc75e69a32a; гоночный
оверлей = GT2.OVL член 0) и проверено на работающем оригинале (`gt2play --smoke-log`, `--prims`). Порт:
`src/gt2view/particles.*` (`SmokePool`), текстуры - `SceneAssets::LoadSmokeTextures`, в игре - `tools/gt2game`
(флаг `--no-particles`). Внешние источники не использовались.

## Итог

- В гонке есть ОДИН вид частиц: дым из-под колёс (серые спрайты с аддитивным смешиванием). Он порождается только
  уровнем юза колеса (wheel + 0x1C >= 0x80). Уровни «дыма» (+0x1D) и «пыли» (+0x1F) рисованием не читаются - они
  идут только в звук (см. ниже).
- Следов шин (skid marks) на дороге оригинал НЕ рисует. Доказательство: в коде оверлея байт юза колеса читается
  только в 0x8001358C / 0x80013624 (порождение дыма, `lb/lbu 0x4A8(s2)` относительно записи машины); других чтений
  +0x1C колеса (побайтно, полусловом, словом; смещения 0x47C от тела и 0x4A8 от машины, базовые указатели колеса
  body + 0x460) в диапазоне 0x80010000..0x800A0000 нет. В захвате `work/play/prims_smoke_3600.txt` (8 полей, 60+
  частиц в кадре) полупрозрачные примитивы - только четыре группы: отражения кузова (clut 7FD7, 1002 шт.), тени
  машин (нетекстурные 3A/32, 324), дым (clut 7F96, 173 - все объяснены портом) и слой облаков задника (clut 7C69, 3);
  ничего похожего на декали следов.
- Вид 1 (спрайт 48x48, crstim.arc запись 1) отрисовщик поддерживает, но ни одна процедура гоночного оверлея его
  не порождает (единственный вызов аллокатора 0x800168A4 - из 0x800133F0 с a1 = 0).

## Пул 0x800ADA0C (= 0x800A9500 + 0x450C)

Заголовок 0x18 байт, затем 256 записей по 0x18 байт.

| Смещение | Поле | Значение после 0x8001681C |
|---|---|---|
| +0x00 | s32 rise: прибавка к позиции Y за кадр (16.16 м, ~1 см; дым поднимается) | 0x444 |
| +0x04 | s32 fadeRate вида 0 | 0x90 |
| +0x08 | s32 fadeRate вида 1 | 0x48 |
| +0x0C | s32 growth: прибавка к размеру за кадр | 8 |
| +0x10 | s16 счётчик выделений 0..15 (НЕ сбрасывается при загрузке гонки) | - |
| +0x12 | s16 голова активного списка (новейшая запись первая), -1 = пусто | -1 |
| +0x14 | s16 голова свободного списка | 0 |

Запись (0x18 байт):

| Смещение | Поле |
|---|---|
| +0x00 | s16 вид (0 дым, 1 - неиспользуемый спрайт 48x48) |
| +0x02 | s16 следующая запись списка, -1 = конец |
| +0x04 | s16 размер (полуразмер спрайта, 1/64 м); 0 при порождении - в этом кадре не рисуется |
| +0x06 | s16 яркость: (уровень юза << 4) при порождении; запись умирает, когда становится < 0 |
| +0x08 | u16 x ^ y ^ z позиции порождения (младшие 16 бит); поворот спрайта = & 0xFFF |
| +0x0A | s16 убыль яркости за кадр = fadeRate[вид] * k >> 12, k = s16-таблица 0x8002F4F8[счётчик] (16 множителей, 4096 = 1.0: значения 1, 1.25, 1.5, 2 в перемешанном порядке; читается с диска из оверлея, `SmokePool::LoadFadeScale`) |
| +0x0C | s32[3] позиция в мире, 16.16 м (оси рендера: x, y вверх, z) |

Время жизни частицы: (юз << 4) / убыль = 0x800..0xFF0 / 0x90..0x120 = 7..28 кадров (0.25..0.9 с при 30 Гц);
полуразмер растёт на 8/64 м = 12.5 см за кадр.

## Процедуры

| Адрес | Что делает |
|---|---|
| 0x8001681C | Загрузка гонки (вызов 0x80015A28 из 0x8001584C): обнуляет записи, цепляет все в свободный список (next = i + 1, последняя -1), константы заголовка. |
| 0x800168A4 | Выделение (a0 = пул, a1 = вид): нет свободных или байт 0x801D5864 (полей на кадр) < 2 -> 0. Иначе голова свободного списка -> голова активного, вид, убыль (см. выше), счётчик + 1 по модулю 16. Позицию/размер/яркость заполняет вызывающий. |
| 0x80016978 | Раз в кадр из BeginFrame 0x80015B64 (вызов 0x80015D14), ДО физики кадра: для каждой активной записи яркость -= убыль; если >= 0: позиция Y += rise, размер += growth; иначе запись снимается в свободный список. |
| 0x800133F0 | Преобразование машины для рендера (кадровый драйвер 0x8003EBF0 вызывает его для машин 0..N-1 ПОСЛЕ физики). Цикл по 4 колёсам: запись колеса car + 0x7C4 + w * 0x10 = {x, y, z} (1/4096 м, оси модели) с y = опорная высота оси (body + 0x134 + ось * 0x34) - ход подвески (wheel + 0x10); если (s8)юз колеса (car + 0x4A8 + w * 0x68 = wheel + 0x1C) < 0 - частица вида 0 в точке матрица машины (car + 0x81C / + 0x830) x (x, y, z) << 4 (0x8007AFC0 / 0x8007AF60 / 0x8007B008 -> ApplyMatrixLV 0x8008220C: ровно floor(R . v / 4096) + t), угол = x ^ y ^ z, размер 0, яркость = юз << 4. |
| 0x80017FA0 | Настройка машины (вызов из 0x80013164): x записи колеса = -/+ половина колеи оси (car + 0x44 / + 0x46 = body.halfTrack[ось]; левые колёса - отрицательные), z = третье s16 записи колеса .cdo (файл + 0x24 + w * 8; `CarWheelOffset::x` нашего парсера). |
| 0x8002EB60 | Отрисовка (a0 = пул, a1 = вид; из 0x8001545C, вызов 0x800154E0, только основной вид - не зеркало). Матрица вида: вращение view + 0x08, смещение view + 0x28 (прибавляется к позиции до >> 10), OFX/OFY view + 0x5C / + 0x60, H view + 0x64. Для записи с размером != 0: V = (позиция + смещение) >> 10 (1/64 м), нужна |V| < 0x8000 по всем осям; RTPS с TR = 0, DQA = размер, DQB = 0; пропуск при любом флаге ошибки GTE (FLAG бит 31) и при радиусе MAC0 >> 16 >= 256. Иначе POLY_FT4 (код 0x2E: текстурный, полупрозрачный, модулированный), центр (SX2, SY2), a = r sin(угол) >> 12, b = r cos(угол) >> 12, углы v0 (x - b + a, y - a - b), v1 (x + b + a, y + a - b), v2 (x - b - a, y - a + b), v3 (x + b - a, y + a + b); серый = яркость >> 5 (вид 1: >> 3); в таблицу упорядочивания по индексу min(SZ3 >> 3, 0xFFF) (база OT - scratchpad 0x1F800064). |

Константы спрайта (непосредственные операнды 0x8002EB60):

| Вид | uv0 / uv1 / uv2 / uv3 | CLUT | tpage |
|---|---|---|---|
| 0 | (128, 0) / (159, 0) / (128, 31) / (159, 31) | 0x7F96 = (352, 510) | 0x0029: страница (576, 0), 4 бита, режим 1 (B + F) |
| 1 | (192, 0) / (239, 0) / (192, 47) / (239, 47) | 0x7F97 = (368, 510) | 0x0029 |

## Текстуры (`crstim.arc` в корне GT2.VOL)

При загрузке гонки 0x800274D4 читает файл 0x6D (`crstim.arc`) и вызывает 0x8002EB08, которая переписывает
заголовки двух TIM (прямоугольники CLUT / изображения из 0x8002F90C.. 0x8002F924) и загружает их:

- запись 2 (4-битный TIM 32x32 текселя, 8x32 слов) -> изображение (608, 0), CLUT (352, 510) - спрайт дыма;
- запись 1 (4-бит, 48x48) -> изображение (624, 0), CLUT (368, 510) - спрайт вида 1.

Проверено по VRAM захвата `work/play/prims_3600.txt.vram.bin`: изображение записи 2 - 256/256 слов, CLUT 16/16;
запись 1 - 576/576 и 16/16. В CLUT записи 2 индексы 0 и 15 = 0x0000 (прозрачные), остальные 14 - серые с битом
STP (все непрозрачные тексели полупрозрачны), поэтому смешивание аддитивное на всём спрайте.
(Запись 0 той же процедурой идёт в (608, 64) с CLUT (368, 509) - это текстура "свечений" (glow-записи чанков и моделей
трассы, u 128..191, v 64..127, CLUT 0x7F57; код 0x80020A00 / 0x800205EC / 0x8001FBA8, см. track_tro.md "Glow records").)

## Кто ещё читает уровни эффектов колёс

0x800146D8 (цикл 0x800149AC..0x80014A2C, по колёсам с разбором поверхности wheel + 0x14): суммирует +0x1D (дым)
и +0x1F (пыль) и пишет уровни звука машины (car + 0xAAA.., объект звука car + 0xAA4). В рисование не идут.

## Проверка

- `gt2play --smoke-log <txt>` (dev): пул зеркалируется нативно - на вызове 0x80016978 наш `Update()`, на вызове
  0x8002EB60 наше порождение по записям машин гостя и сравнение всего активного списка и заголовка с пулом гостя.
  Заставка Сиэтла, поля 1955..3605: 780 кадров из 780 совпали (до 136 активных частиц), `work/play/smoke_log_attract.txt`;
  отдельный прогон до 2567: 306/306 (`smoke_log_2560.txt`); лицензия B-1 : 581/581 кадров без
  дыма у обоих (`smoke_log_license.txt`).
- `gt2play --prims`: на вызове отрисовки печатаются `# smoke-ours:` = `SmokePool::BuildPrimitives` пула гостя с видом
  гостя (целочисленная RTPS с делением UNR); сравнение с GP0-примитивами clut 7F96 того же кадра:
  `prims_smoke_3600.txt` - 56/56, 58/58, 59/59 идентичны (координаты, UV, CLUT, tpage, цвет);
  `prims_smoke_2560.txt` - 34/34, 41/41, 50/50.
- Нативный рендер (`SmokePool::AppendBillboards`): тот же спрайт как квадрат в плоскости камеры с полуразмером
  size / 64 м (эквивалент r = size * H / SZ оригинала), поворот и UV как у PS1-квада, серый x текстура / 128,
  режим 1; отбрасывание - те же условия (|V| < 0x8000, H < 2 SZ, r < 256 на 240-строчном кадре). Кадры:
  `work/play/particles_orig_3600.png` / `particles_native_3600.png` (gt2play, дым пула гостя нашим рендером при
  камере оригинала), `particles_orig_2610.png` / `particles_native_2610.png`, игра:
  `particles_native_launch_120.png`, `particles_native_grid6_90.png` (с дымом) и `_off.png` (`--no-particles`).
- Отличие, оставленное сознательно: оригинал сортирует спрайт по таблице упорядочивания (центр спрайта против
  средней глубины полигонов), наш рендер - z-буфером по плоскости спрайта; часть спрайта, попавшая «в кузов» ближе
  плоскости, у нас скрыта. Разбор 2026-09-19: спрайт - квадрат в плоскости камеры, его глубина по всей площади равна
  глубине центра (SZ оригинала), так что z-тест уже сравнивает «центр спрайта» с поверхностью; отличие остаётся только
  там, где оригинал сравнивает с ОДНИМ числом на полигон (индекс OT по дальнему/среднему углу), а мы - попиксельно.
  Воспроизвести это можно только сортировкой всей сцены по полигонам (без z-буфера) - в нашем рендере не делается;
  захвата дыма у кузова в гонке игрока, где разница была бы видна, нет.
